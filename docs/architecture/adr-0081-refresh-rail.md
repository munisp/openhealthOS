# ADR-0081: The refresh rail — a gate and its fix read one recipe book

- Status: accepted
- Date: 2026-11-11
- Supersedes: nothing. Completes ADR-0080 (the freshness gate) with the
  fix path it named but did not provide.

## Context

ADR-0080's freshness gate names WHAT is stale: every registered payload's
committed bytes are compared to what its exporter produces today. But the
gate stopped at naming. When it went red, the fix was tribal knowledge:
which package holds the exporter, which snippet writes the file, which
path does the payload live at, which of the hash-family exporters prints
digests versus writes files? An operator facing a red gate had to
reverse-engineer the gate's own tables to repair what it found.

A gate without a fix path is friction. Worse, a fix path written
SEPARATELY from the gate is drift waiting to happen: two lists of
exporters, two sets of snippets, two ideas of where payloads live — and
nothing but vigilance keeping them equal.

## Decision

1. **`packages/proofindex/recipes.py` is the ONE recipe book.** 24
   recipes (19 file-kind, 5 hash-kind covering 12 payloads) carry name,
   package, kind, write snippet, and output paths; hash-kind recipes
   additionally carry the probe snippet. The book was generated by
   importing the gate's own tables — the hash probe snippets are embedded
   byte-identically, not retyped.

2. **The gate READS the book.** `TestExporterFreshness`'s file- and
   hash-family tables are derived from `recipes.RECIPES`, and two
   cross-pin tests fail the suite if the book and the determinism gate
   ever disagree: every recipe must have a determinism entry, and every
   hash probe must be byte-identical to its determinism snippet.

3. **The fix READS the book.** `packages/proofindex/refresh.py`
   regenerates every payload in one run:

       python3 packages/proofindex/refresh.py          # regenerate all
       python3 packages/proofindex/refresh.py --list   # show recipes

   The executor is INJECTED into `run_recipes`: the CLI supplies
   subprocesses, demos and tests supply fixtures. Results are named, not
   silent: `regenerated` (changed paths and 12-char digests named),
   `already-fresh`, `runner-error` (a raise is a verdict, never a
   crash), `absent-after-write` (a recipe that runs clean but produces
   no payload is a defect, named red).

4. **Recipe-less payloads are impossible in the real tree.** The
   coverage pin turns any registered payload without a recipe into a
   suite failure; the drill board states the amber fate only because the
   pin makes it unreachable.

## Consequences

- One command repairs a red freshness gate: `refresh.py`, then commit.
- Adding a payload means adding ONE recipe; gate, rail, and coverage pin
  all learn it from the same line.
- A census that can be checked IS checked: the refreshproof demo pins
  its census numbers against the live recipe book — the demo cannot
  quietly lag the machinery it describes.

## Alternatives considered

- **Keep refresh snippets in a separate config.** Rejected: two books
  drift; the gate would be auditing evidence its fix path cannot see.
- **Make refresh.py shell out per recipe without injection.** Rejected:
  untestable without subprocesses, and contrary to the injected-executor
  doctrine that keeps proofindex stdlib-only (ADR-0005).
- **Regenerate everything unconditionally on every commit.** Rejected:
  freshness is a gate (ADR-0080); the rail is the repair, run on demand,
  with before/after digests so the diff is auditable.
