# ADR-0019: Emergency dispatch with integrated case management and CRM

Status: accepted (2026-10-18)

## Context

Africa's missing emergency piece is not the ambulance — it is the
dispatcher. Most states have no single number a citizen can call, text,
or message when someone is bleeding; the nearest facility that can
actually help is unknown to the caller; and once a call ends, nobody
owes the caller anything — no arrival confirmation, no callback, no
welfare check. Emergencies are lost in the gap between *dispatched* and
*actually cared for*.

The user asked for a paramedic/ambulatory capability built on the FHIR
IG foundation, reachable over a number — possibly WhatsApp — that
geolocates the patient and the closest appropriate facility; and then
for **robust case management and CRM integrated into emergency
dispatch**, so every emergency has an owner and a follow-through.

## Decision

A new Go stdlib+pgx service, `services/dispatch-service`, with three
planes in one deployment unit (they share a lifecycle and a store):

### 1. Incident plane (the dispatcher)

- **One number, many channels**: `POST /sos` (app/USSD gateway) and a
  **WhatsApp Cloud API webhook** — `GET` verification handshake
  (`WHATSAPP_VERIFY_TOKEN` + `hub.challenge`) and `POST` inbound that
  turns text messages and location pins into intakes. The webhook
  **always answers 200** — a non-200 makes WhatsApp retry forever, and
  a retry loop is an availability incident, not a validation signal.
- **Deterministic triage** (red/orange/green), keyword protocol with
  red flags first (bleeding, unconscious, breathing, chest pain,
  convulsion, stroke, obstetric). The protocol is data:
  `DISPATCH_TRIAGE_FILE` overrides it, a bad file panics at boot —
  same pattern as the vitals rules file. Deterministic beats clever
  when a life is on the line and the reviewer is a court.
- **Repeat-SOS dedupe**: the same caller inside a 10-minute window
  updates the open incident (latest complaint wins, coords refreshed)
  instead of cloning it. This is also what makes the WhatsApp pattern
  work — a bare location pin follows the text and *completes* the
  incident, triggering assignment.
- **Tiered facility assignment** over the registry's
  `/facilities/near`: emergency amenity within 100km → hospital level
  within 150km → anything within 200km. The tier used is recorded on
  the incident timeline so a downgrade is visible, not silent.
- **Lifecycle**: received → triaged → dispatched → acknowledged →
  on_scene → transported → closed (| cancelled), enforced as a state
  machine; every transition is an attributed timeline entry and a
  `dispatch_update` event on the notification rail, so the caller hears
  "help is on the way / has arrived / case closed — we will check on
  you in 48 hours, reply STOP to opt out".

### 2. Case plane (what the system owes the caller)

An incident is what happened at 14:32. A **case** is everything the
system owes the caller afterwards.

- Cases **open automatically** from red/orange triage — never rely on a
  human remembering paperwork mid-crisis. Green stays informational.
- One open case per caller (repeat emergencies fold in, they don't
  stack), exactly **one accountable owner** at a time.
- Tasks are **generated by the lifecycle, not typed by hand**:
  `arrival_check` on dispatch, due on the triage SLA (red 30min,
  orange 4h, green 24h); `followup_48h` welfare call on incident
  closure. Humans add `callback`/`custom` tasks on top.
- `GET /tasks/overdue` is the SLA made visible — the dispatcher's
  guilt list, oldest first.
- Outcomes are **coded, not prose**: `resolved_care_received |
  referred_onward | self_resolved | false_alarm | lost_to_followup |
  deceased`. A case cannot resolve without one — the aggregate of
  outcomes is the service's quality measure, and it feeds the
  ADR-0019+ quality engine.

### 3. CRM plane (the caller as a person)

- **Contact** keyed by phone: patient link when known, preferred
  channel, language, tags, first/last contact, interaction count.
  Created automatically on first SOS.
- **Interaction log**: every touch in order (inbound SOS, outbound
  callback, status update, note), attributed, channel-stamped — the
  institutional memory that survives a dispatcher shift change.
- **Consent (NDPA)**: an SOS implies consent to be helped, so
  `consent_follow_up` defaults true — but it is revocable at any time
  (`POST /contacts/{phone}/consent`), and the task rail respects it:
  no 48-hour welfare task is queued for a caller who opted out.

### Events

`emergency_dispatch` and `dispatch_update` fire to the notification
service, whose `renderMessage` turns them into SMS-length messages with
the `OpenHealth:` sender prefix. Event delivery is best-effort and
never fatal — the incident exists whether or not the SMS leaves today.

## FHIR mapping

The domain maps onto the existing OpenHealthOS IG without new
licensing surface: an incident is an `Encounter` of class `EMER`
(profiled as `openhealth-encounter`); facility matching resolves
against `Location` resources; the dispatch rail rides the same
notification subscription envelope as every other domain event.
Measure definitions for response-time and follow-up-completion quality
measures land with the quality engine (separate ADR entry).

## Consequences

- One service to deploy, one migration (`0015_dispatch`), one demo
  (`demo/dispatch.sh`) that proves the whole chain in memory:
  WhatsApp SOS → red triage → nearest emergency facility → contact +
  interaction log → auto-opened case → SLA arrival task → lifecycle to
  closure → 48h welfare task → consent revocation respected.
- The CRM is deliberately small: phone-keyed contacts and ordered
  interactions. It is not a marketing CRM; it is the memory an
  emergency service needs to not lose people.
- Nothing here embeds restricted-licence components: triage, state
  machines, dedupe, and the CRM are stdlib Go; WhatsApp integration is
  the public Cloud API over HTTPS.

## Honest limits

- Cell-tower geolocation is coarse; the WhatsApp pin is precise but
  requires the caller to send it. The timeline records `loc_source`
  so responders know which they have.
- Triage keywords are English-first; the protocol file mechanism exists
  precisely so states can ship Hausa/Yoruba/Igbo keyword sets without
  a code change.
- The dispatcher cannot create ambulances. It makes the demand
  visible, routed, and owed — supply is a policy decision the data
  now supports.
